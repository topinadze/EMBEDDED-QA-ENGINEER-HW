## 1. Призначення документу

Цей документ описує функціональні та нефункціональні вимоги до прошивки SENTRY-C1. Документ є основою для написання тест-кейсів, проведення ревʼю коду та онбордингу нових учасників команди.

---

## 2. Огляд продукту

SENTRY-C1 — референсний вузол моніторингу на базі ESP32-S3 з консольним інтерфейсом керування через UART (115200 8N1). Пристрій реалізує типовий для embedded-продуктів набір підсистем:

- рольова модель доступу на основі сесій
- збір і зберігання телеметрії
- порогова сигналізація з керуванням індикатором
- персистентна конфігурація (fake NVS)
- асинхронна черга сервісних задач
- діагностичний режим розробника

Використовується як навчальний стенд. Фізична периферія (кнопки) для тестування не потрібна — весь функціонал доступний через UART CLI.

## 3. Апаратна база

| Компонент | Деталі |
|-----------|--------|
| MCU | ESP32-S3 |
| Інтерфейс | UART0, 115200 8N1 |
| Індикатор | GPIO4 (LED, active HIGH) |
| Кнопка KEY1 | GPIO41, pull-up, active LOW |
| Кнопка KEY2 | GPIO40, pull-up, active LOW |
| Кнопка KEY3 | GPIO39, pull-up, active LOW |
| Кнопка KEY4 | GPIO38, pull-up, active LOW |

Фізичні кнопки електрично підключені, але в поточній версії прошивки **не реалізовані** як команди CLI (детальніше — розділ 11).

## 4. Рівні доступу

Пристрій має три рівні авторизації. Більшість команд потребує активної сесії.

| Рівень | Як отримати | Доступні команди |
|--------|-------------|-----------------|
| `AUTH_NONE` | За замовчуванням / після `logout` | `register`, `login`, `help` |
| `AUTH_USER` | Після успішного `login` | Всі команди загального набору |
| `AUTH_DEV` | Після `login key` з правильним ключем | Всі команди + `dev *` |

Сесія не має таймауту — діє до явного `logout` або перезавантаження. Активність сесії відстежується через tick-лічильник.

## 5. Фіча: Керування доступом

### 5.1. Реєстрація профілю

На пристрої може існувати **один** локальний профіль користувача. Профіль зберігається у волатильній пам'яті (RAM) і скидається при перезавантаженні.

**Поведінка:**
- `register <login> <password>` — створює профіль, якщо його ще немає
- Повторна реєстрація заблокована: якщо профіль вже існує — команда відхиляється з попередженням
- Після успішної реєстрації пристрій виводить підтвердження з логіном та рівнем доступу

**Обмеження:**
- Один профіль на пристрій
- Профіль не персистується між перезавантаженнями

### 5.2. Вхід у сесію

**Поведінка:**
- `login <login> <password>` — перевіряє облікові дані, відкриває сесію рівня `AUTH_USER`
- Якщо профіль не зареєстрований — команда відхиляється
- Якщо сесія вже активна — команда відхиляється з пропозицією спочатку виконати `logout`
- Після успішного входу виводиться вітання з поточним станом сенсора, сигналізації та heap

### 5.3. Захист від перебору паролів (rate limit)

**Поведінка:**
- Кожна невдала спроба входу інкрементує лічильник невдалих спроб
- Після **3 послідовних** невдалих спроб обліковий запис блокується на **30 секунд**
- Під час блокування будь-яка спроба `login` відхиляється з повідомленням про кількість секунд до розблокування
- Після закінчення 30 секунд лічильник скидається автоматично при наступній спробі входу
- Успішний вхід також скидає лічильник

**Сценарій відтворення:**
```
login user wrongpass   // → FAILED. Attempts: 1/3
login user wrongpass   // → FAILED. Attempts: 2/3
login user wrongpass   // → FAILED. Attempts: 3/3 → Account locked for 30 s
login user correctpass // → Account locked. Try again in 27 s.
// (чекаємо 30 с)
login user correctpass // → Session Started
```

### 5.4. Режим розробника

**Поведінка:**
- `login key` — запускає інтерактивний промпт `key>`, дає 3 спроби ввести крипто-ключ
- `login key <key>` — скорочений варіант одним рядком
- Правильний ключ → рівень `AUTH_DEV`, виводиться підтвердження з переліком нових команд
- Неправильний ключ × 3 → відмова, рівень залишається `AUTH_USER`
- Режим розробника діє до `logout` або перезавантаження

### 5.5. Завершення сесії

**Поведінка:**
- `logout` — зупиняє сенсор, знімає сигналізацію, скидає рівень до `AUTH_NONE`, гасить LED
- Якщо сесії немає — виводить попередження

## 6. Фіча: Базові системні команди

Ці команди доступні **без активної сесії** (крім `status`, `start`, `led *` — вони потребують `AUTH_USER`).

| Команда | Опис |
|---------|------|
| `help` | Виводить повний перелік команд |
| `status` | Стан кнопок, LED, WiFi-модуля, heap |
| `start` | 5-крокова послідовність ініціалізації з логом прогресу |
| `led on` | Вмикає LED (GPIO4) |
| `led off` | Вимикає LED (GPIO4) |
| `led blink <n>` | Блимає LED n разів (діапазон: 1..20) |
| `reboot` | Перезавантажує пристрій |

### 6.1. Режим блимання LED

**Поведінка:**
- Приймає ціле число в діапазоні 1..20
- Значення поза діапазоном → команда відхиляється з повідомленням про помилку
- Виконується синхронно: CLI не обробляє інші команди під час блимання
- Кожен цикл: LED ON 150 мс → LED OFF 150 мс
- Після завершення послідовності LED залишається у вимкненому стані
- Виводить лог початку та завершення послідовності

**Сценарій:**
```
led blink 5    // → [LED] Blinking 5 time(s)... → [LED] Blink sequence done.
led blink 0    // → [LED] Blink count out of range (1..20).
led blink 25   // → [LED] Blink count out of range (1..20).
```

## 7. Фіча: Телеметрія (Sensor)

Потребує `AUTH_USER`. Збір телеметрії виконується у фоновій FreeRTOS-задачі з конфігурованим інтервалом.

| Команда | Опис |
|---------|------|
| `sensor start` | Запускає збір телеметрії |
| `sensor stop` | Зупиняє збір, скидає лічильник показань |
| `sensor set <value>` | Встановлює значення вручну (manual override) |
| `sensor history` | Виводить буфер останніх 10 показань |

### 7.1. Автоматичний режим

**Поведінка:**
- Кожні `sensor_interval` мс (за замовчуванням 3000 мс) виводить показання: температура, вологість, тиск, ADC raw, якість сигналу
- Показання нумеруються починаючи з `#1`; лічильник скидається при `sensor stop`
- Кожне 7-е показання має знижену якість (`DEGRADED`)
- Значення температури передається в підсистему сигналізації як `alarm_last_val`
- При `AUTH_NONE` (logout) збір автоматично призупиняється

### 7.2. Ручний режим (override)

**Поведінка:**
- `sensor set <value>` — фіксує значення, яке використовується замість автоматичного
- Режим override активується незалежно від стану `sensor start/stop`
- `sensor start` після `sensor set` скидає override і повертає автоматичний режим

### 7.3. Буфер історії показань

**Поведінка:**
- Пристрій веде кільцевий буфер останніх **10** показань температури (тільки в автоматичному режимі, override не записується)
- `sensor history` — виводить вміст буфера від найстарішого до найновішого з порядковим номером
- Якщо буфер порожній — виводить відповідне повідомлення
- Буфер доступний незалежно від поточного стану сенсора (running/stopped)
- Буфер не зберігається між перезавантаженнями

**Сценарій:**
```
sensor start
// чекаємо кілька показань...
sensor stop
sensor history   // → [1] temp: 23.20 C  [2] temp: 23.50 C  ...
```

## 8. Фіча: Порогова сигналізація (Alarm)

Потребує `AUTH_USER`. Незалежна підсистема, яка моніторить значення телеметрії у фоновій задачі (перевірка кожну 1 секунду).

| Команда | Опис |
|---------|------|
| `alarm arm` | Активує моніторинг |
| `alarm disarm` | Деактивує моніторинг |
| `alarm clear` | Скидає стан TRIGGERED → CLEARED |
| `alarm status` | Виводить поточний стан підсистеми |

### 8.1. Стани сигналізації

```
DISARMED ──(arm)──► ARMED ──(value >= threshold)──► TRIGGERED
    ▲                  │                                  │
    └──(disarm)────────┘          (clear)                 │
    ◄──────────────────────────────────────────────────────┘
                                                      CLEARED
                                                          │
                                                    (arm)─┘
```

### 8.2. Поведінка

- Спрацювання: якщо `alarm_last_val >= alarm_threshold` → стан `TRIGGERED`, LED примусово вмикається
- `alarm clear` доступна лише зі стану `TRIGGERED`; зі стану `ARMED` або `DISARMED` — відхиляється з попередженням
- Моніторинг автоматично призупиняється якщо: сесія завершена (`AUTH_NONE`), сенсор зупинений, або активний job калібрування (`alarm_inhibit = true`)
- `alarm status` виводить: стан, поріг, останнє значення, стан сенсора, стан LED

### 8.3. Залежності

| Умова | Вплив на alarm |
|-------|---------------|
| `AUTH_NONE` | Моніторинг призупинено |
| `sensor stop` | Моніторинг призупинено |
| `job calibrate` активний | Моніторинг призупинено (`inhibit`) |
| `job cancel` | Моніторинг відновлено (`inhibit` знімається) |

## 9. Фіча: Конфігурація

Потребує `AUTH_USER`. Два параметри виконання зберігаються у двох структурах: `s_cfg` (робоча) та `s_cfg_nvs` (fake NVS — персистована копія).

| Команда | Опис |
|---------|------|
| `config set <key> <value>` | Змінює параметр у робочій конфігурації |
| `config get <key>` | Читає поточне значення параметра |
| `config save` | Зберігає робочу конфігурацію у fake NVS |
| `config load` | Завантажує конфігурацію з fake NVS у робочу |

### 9.1. Параметри

| Ключ | Тип | Діапазон | За замовчуванням | Опис |
|------|-----|----------|-----------------|------|
| `sensor_interval` | int (мс) | 500..60000 | 3000 | Інтервал між показаннями сенсора |
| `alarm_threshold` | int | 0..10000 | 80 | Поріг спрацювання сигналізації |

### 9.2. Поведінка

- `config set` — застосовує зміну негайно, виставляє прапор `saved = false`, виводить попередження про незбережений стан
- `config save` — копіює `s_cfg → s_cfg_nvs`, виставляє `saved = true`
- `config load` — якщо `s_cfg_nvs.saved == false` (збереження ніколи не виконувалось) — виводить **WARNING** про завантаження дефолтних значень; завантажує `s_cfg_nvs → s_cfg` в будь-якому випадку
- Зміни `sensor_interval` впливають на інтервал фонової задачі сенсора з наступного циклу
- Зміни `alarm_threshold` впливають на наступну перевірку в alarm-задачі

## 10. Фіча: Черга сервісних задач (Job Queue)

Потребує `AUTH_USER`. Асинхронна черга для виконання фонових сервісних операцій.

| Команда | Опис |
|---------|------|
| `job add calibrate` | Додає задачу калібрування в чергу |
| `job list` | Виводить поточний стан черги |
| `job cancel <id>` | Скасовує задачу за ID |

### 10.1. Параметри черги

| Параметр | Значення |
|----------|---------|
| Максимальний розмір черги | 4 задачі |
| Підтримувані типи задач | `calibrate` |
| Одночасно активних `calibrate` | не більше 1 |

### 10.2. Стани задачі

```
PENDING ──(запуск)──► RUNNING ──(завершення)──► DONE
   │                     │
   └──(cancel)──► CANCELLED
```

### 10.3. Поведінка

- `job add calibrate` — перевіряє чи немає вже активного `calibrate` (PENDING або RUNNING); якщо є — відхиляє
- Перед перевіркою місця в черзі автоматично видаляє завершені (DONE/CANCELLED) слоти — черга звільняється без ручного втручання
- Задача виконується у окремій FreeRTOS-задачі (`job_cal`), виводить 4-крокову послідовність (~4 секунди)
- На час виконання `calibrate` встановлює `alarm_inhibit = true` → сигналізація призупиняється
- Після завершення (`DONE`) — `alarm_inhibit = false`, моніторинг відновлюється
- `job cancel <id>` — для задачі `calibrate` також знімає `alarm_inhibit = false`
- `job list` виводить: ID, назву, стан, час від постановки в чергу

## 11. Фіча: Діагностика (Dev mode)

Потребує `AUTH_DEV`. Інженерний інтерфейс для перегляду внутрішнього стану системи.

| Команда | Опис |
|---------|------|
| `dev info` | Повна системна інформація: chip, IDF, heap, uptime, auth, sensor, alarm, config |
| `dev heap` | Деталі використання heap: free, min free, used, health |
| `dev tasks` | Список FreeRTOS-задач з пріоритетами та розміром стеку |
| `dev gpio` | Сирий стан всіх GPIO (KEY1-4, LED) |

`dev tasks` також виводить: кількість задач у черзі, стан `alarm_inhibit`.

## 12. Фіча: Фізичні кнопки — Not Implemented

Плата має чотири фізичні кнопки (GPIO38-41) з номінальним призначенням:

| Кнопка | GPIO | Номінальне призначення |
|--------|------|----------------------|
| KEY1 | GPIO41 | Утримання — LED ON |
| KEY2 | GPIO40 | Натискання — toggle LED |
| KEY3 | GPIO39 | Натискання — вивід статусу в лог |
| KEY4 | GPIO38 | Лічильник натискань |

У поточній версії прошивки ця функціональність **не реалізована**. Стан виводів доступний лише через `dev gpio`. Тест-кейси на фізичне керування через кнопки не потрібні.

## 13. Нефункціональні вимоги

| Вимога | Деталі |
|--------|--------|
| Таймаут сесії | Відсутній — сесія діє до `logout` або reboot |
| Персистентність | Тільки конфігурація через `config save`; профіль, сесія, буфер історії — волатильні |
| Стійкість до некоректного вводу | Невідома команда → повідомлення про помилку, без reboot/hang |
| Конкурентний доступ | CLI-задача та фонові задачі (sensor, alarm, job) працюють паралельно через FreeRTOS |
| Вивід логів | Всі логи через `ESP_LOG*`, виводяться через той самий UART з mutex-захистом |
