# DZ17 manual test plan

## 1. New assignment and bench analysis

The new assignment is the SENTRY SWM-2 lab module. The required baseline is the ESP32-S3 DevKit running firmware 2.1.0, initially installed from the merged binary by erasing flash and writing at address `0x0`. The operator controls it over UART at 115200 8N1. The bench uses HC-SR04 (TRIG GPIO5 / ECHO GPIO18), a relay (GPIO8) and indicator diode (GPIO4), the built-in RGB LED (GPIO48), and buttons K1–K4 (GPIO41, GPIO40, GPIO39, GPIO38). All modules are powered at 3.3 V. Wi-Fi is 2.4 GHz with internet access.

The operator must confirm the firmware from device output rather than the filename. Start with `connect`, register and log in as required. The Wi-Fi network, account, settings, relay counters, sensor configuration, health configuration, Guard PIN/zone, and OTA state can persist. Record relevant initial state before changing it. `logout`, `reboot`, flash erase, OTA, Wi-Fi disconnect, relay activity, Guard alarm, and changes to persistent configuration have explicit state or physical effects; plan cleanup and recovery.

The test sequence is: baseline 2.1.0 checks; OTA upgrade to 2.3.0 and OTA-10 retention checks; 2.3.0 feature checks and regression of applicable 2.1.0 coverage; OTA rollback/downgrade/error scenarios; safe exploratory testing of undocumented commands. Every hardware result remains unverified until the operator performs the action and saves the corresponding evidence.

**Current interactive distance characterization (implemented, NOT RUN after this change):** The first iteration now requests a ruler-measured target distance, explains the exact placement and observation, and runs one `distance` measurement before asking whether to continue. Only subsequent iterations begin with the continue prompt; choosing no ends the series. Each sample requires a valid single echo and compares the signed difference with ±0.50 cm to allow for uncertainty when measuring/positioning the target. This is a setup tolerance, not a PRD-defined sensor accuracy specification. The test retains the relay-auto-off/state guard, checks sonar alert IDs emitted by its own measurement, and does not ACK or clear alerts; it attaches the full comparison table after the operator ends the series.

**Wi-Fi LED-check procedure:** Manual checks use UART-confirmed Wi-Fi/login state, require the Beacon off and no higher-priority LM-8 indication, and avoid protected `lamp status` queries while logged out. Link fixtures establish and restore connectivity without forcing login; successful connect remains persistent because it saves the configured profile. WF-5 capture starts after readiness confirmation.

**Wi-Fi UART response handling:** Connect/reconnect require explicit association and IP events and return early on recognized errors; reconnect success is not inferred from association alone. Status waits for the terminal `heap:` line or an explicit command error, retries once if no terminal marker arrives, then fails with the captured response. Disconnect waits for `[LINK] disconnected` or W115; negative-input tests wait directly for E111/E112. Deadlines are upper bounds, and missing expected events fail with the captured UART excerpt.

**Wi-Fi version and LED checks:** LED prompts ask whether the operator sees the color corresponding to UART-confirmed Wi-Fi/login state. Firmware detection requires a supported firmware-version line with a numeric version, up to three attempts of at most 3 seconds each. Wrong-password validation requires explicit E101 / wrong-password evidence rather than a generic connection-failed message.

**Operator prompt and evidence protocol:** `manual_prepare` must state the action, expected observation, duration, and readiness confirmation before any physical action. Console is the default; optional Telegram uses the same action/observation intent and records the authorized operator response. Prominent category/state icons are aids, not device-state evidence. Lamp checks show the named expected color and RGB reference (terminal sample or Telegram swatch); only the operator can confirm the physical LED. Store operator feedback separately from UART assertions and per-test transcripts. See [the DZ17 gotchas](../.agents/skills/interactive-hardware-tests/references/dz17-gotchas.md) and [README interaction protocol](README.md#safety--interactive-protocol-agentsmd).

## 5. Execution controls and evidence

- Establish version and partition from device-reported output before every firmware-specific test phase. If unexpected, stop and resolve the baseline rather than attributing the failure to the product.
- Keep cases isolated where state permits. Record setup, command/input, expected UART response, actual response, physical observation, cleanup/reboot, and evidence path.
- Console and Telegram manual-check results are operator evidence; UART logs prove only the device messages they contain. Keep both channels attached/correlated to the run and never upgrade a status because a prompt was shown or acknowledged.
- Before every physical action, tell the operator exactly what to do and observe, include duration, and wait for explicit readiness. For a live stream, allow adequate observation time, stop it, and verify it stopped before asking for a manual verdict.
- For multiple UART events caused by one button press, retain all lines after the action; do not treat the first event as the complete result.
- Do not run tests using real Wi-Fi credentials if the terminal/logger cannot reliably redact them. Never store credentials in evidence.
- OTA and state-changing cases require the tester's confirmation and pre-test snapshot. Keep one complete log for each OTA transition, including failed attempt plus successful retry where required.
- `fw_7/tools/README.md` describes local OTA server modes. The OTA error scenario set is mandatory per HW-17. Restore `ota server default` after the local-server cases.
- Hidden-command exploration is a bonus and must not interrupt required acceptance testing or expose credentials/data.
- The pytest defaults exclude `interactive` and `persistent` cases. `-All` behavior is launcher-specific: inspect its marker expression, addopts handling, and collection count before execution. The Distance launcher's `-All` selects its entire module, including physical/persistent cases; collection is not proof they were executed. See [the DZ17 gotchas](../.agents/skills/interactive-hardware-tests/references/dz17-gotchas.md).
