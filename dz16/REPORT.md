# HW-16: Звіт тестування OTA-оновлень Smart Lamp

> Заповнити лише за результатами фактичного тестування ESP32-S3. Не позначати перевірку `PASS` без спостереження очікуваної поведінки. Перед додаванням логів замінити пароль Wi-Fi на `***`.

## 1. Тестове оточення

| Поле | Значення |
|---|---|
| Тестер | `Турчаненко Антон` |
| Період тестування | `2026-10-09–2026-10-12` |
| Плата | ESP32-S3, QFN56, revision v0.2; 8 MB embedded PSRAM (reported by esptool) |
| ОС / UART-термінал | Windows / назву термінала не зафіксовано |
| UART | 115200 8N1, COM4 |
| Wi-Fi | 2.4 GHz, `TopA-node` |
| Початкове прошивання | `station_WiFi_v1.3.0_merged.bin` за [`README.md`](../fw_6/README.md); запис підтверджено esptool v5.4.0, hash verified |
| Джерело очікуваної поведінки | [`PRD.md`](../fw_6/PRD.md) |

**Запис прошивання:** esptool під'єднався до ESP32-S3 на COM4, запустив stub flasher і змінив baud rate на 460800. Flash erase range: `0x00000000–0x000edfff`. Записано 973152 bytes (625254 compressed) за адресою `0x00000000`; hash перевірено. Виконано hard reset через RTS. Окремий boot log безпосередньо після первинного прошивання не збережено; версію 1.3.0 підтверджено пізнішими `version`/OTA логами.

**Перевірки консолі та Wi-Fi:** COM4 відкрито; команда `help` виконана на пристрої (uptime у виводі ~33.5 с), список команд збережено в [`logs/manual/system/1.3.0/help-1.3.0.txt`](logs/manual/system/1.3.0/help-1.3.0.txt). `connect` успішно під'єднався до `TopA-node` і отримав IP; пароль у [`logs/manual/wifi/1.3.0/connect-1.3.0.txt`](logs/manual/wifi/1.3.0/connect-1.3.0.txt) замінено на `***`. Пароль не включати до звіту чи логів.

**Автоматизація перевірки 1.3.0/1.4.0/1.5.0:** pytest-набір з групами `lamp` і `wifi`, незалежними тестами, UART DEBUG-виводом і прикріпленням повного логу до кожного результату Allure підготовлено у [`tests/test_lamp.py`](tests/test_lamp.py). UART-кроки драйвера позначені `@allure.step` і відображають відкриття/закриття з'єднання, надсилання команд, очікування відповіді, розбір стану/версії та прикріплення транскрипту. Напівмануальні перевірки покривають фізичне вмикання/вимикання та Wi-Fi-індикацію, кольори (названі й custom RGB), незмінність LED після відхилення значень, яскравість, режими, таймерне вимкнення, стан після reboot і фізичні кнопкові сценарії K3 для Wi-Fi. Інтерактивні перевірки виключені зі звичайного запуску за замовчуванням і потребують `-s -m interactive`; результат і коментар додаються в Allure, запуск без `-s` зупиняється до відкриття UART. Матриця покриття L-01–L-18 нижче, покриття O-16/O-17 автоматизованими K3-тестами — у розділі 3. Інструкції запуску — у [`README.md`](README.md).

## 4. Баг-репорти

Додати по одному заповненому блоку на кожен відтворюваний дефект. Якщо багів не знайдено, вказати це після завершення всіх перевірок; до того часу залишити статус невизначеним.

### BUG-01: Wi-Fi status та індикація LED не оновлюються після disconnect

- **Версії, у яких відтворюється:** 1.3.0 та 1.4.0.
- **Не перевірено:** 1.5.0.
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** ESP32-S3 підключений до Wi-Fi; лампа вимкнена, LED показує тьмяно-зелений статус з'єднання.
- **Кроки відтворення:**
  1. Виконати `disconnect`.
  2. Виконати `status`.
  3. Виконати `lamp on`, потім `lamp off` і спостерігати за кольором LED.
- **Очікуваний результат:** команда `status` показує `WiFi: disconnected` після роз'єднання ([FR-W4](../fw_6/PRD.md#3-wi-fi)); коли лампа вимкнена, LED показує тьмяно-червоний статус відсутнього Wi-Fi-з'єднання ([FR-W6](../fw_6/PRD.md#3-wi-fi), [FR-L1](../fw_6/PRD.md#4-smart-lamp)).
- **Фактичний результат:** після повідомлення `disconnected` команда `status` повертає `WiFi: connected`, порожній SSID, IP `0.0.0.0` та RSSI `0 dBm`. Після циклу `lamp on`/`lamp off` LED залишається тьмяно-зеленим замість тьмяно-червоного.
- **Доказ (фрагмент UART):**
  ```text
  I (1067154) wifi station: disconnected
  ---- Sent utf8 encoded message: "status\n" ----
  I (1083614) wifi station: WiFi: connected
  I (1083614) wifi station:   SSID:
  I (1083614) wifi station:   IP:   0.0.0.0
  I (1083614) wifi station:   RSSI: 0 dBm
  I (1105094) wifi station: [LAMP] on
  ---- Sent utf8 encoded message: "lamp off\n" ----
  ```
  Повні логи: 1.3.0 — [`logs/manual/wifi/1.3.0/disconnect-status-led-1.3.0.txt`](logs/manual/wifi/1.3.0/disconnect-status-led-1.3.0.txt); 1.4.0 — [`logs/automated/lamp/1.4.0/20261012-test_k3_disconnect_status_and_led.txt`](logs/automated/lamp/1.4.0/20261012-test_k3_disconnect_status_and_led.txt). На 1.4.0 оператор також повідомив, що LED не тьмяно-червоний; це ручне спостереження (відповідь оператора, збережена в Allure-результатах), воно не відображене в UART-транскрипті. Після цього тест змінено: статус і спостереження LED тепер збираються до перевірки та звітуються разом.
- **Відтворюваність:** відтворено на обох протестованих версіях (1/1 на 1.3.0 та 1/1 на 1.4.0).
- **Примітка:** цей баг також відтворювався у DZ14 і був занотований як BUG-01.

### BUG-02: Кнопка K3 не запускає повторне підключення до збереженої Wi-Fi мережі

- **Версії, у яких відтворюється:** 1.3.0 та 1.4.0.
- **Не перевірено:** 1.5.0.
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** ESP32-S3 раніше успішно підключився до Wi-Fi; credentials збережені; K3 доступна.
- **Кроки відтворення:**
  1. Натиснути K3, щоб відключити ESP32 від Wi-Fi.
  2. Переконатися за UART, що пристрій повідомив `disconnected`.
  3. Натиснути K3 ще раз.
  4. Виконати `status` і перевірити, чи почався reconnect та чи отримано IP.
- **Очікуваний результат:** якщо Wi-Fi відключений, K3 запускає підключення до збереженої мережі, показує `[K3] wifi reconnect (saved credentials)` і після успішного підключення пристрій отримує IP ([FR-W5](../fw_6/PRD.md#3-wi-fi)).
- **Фактичний результат:** повторні натискання K3 знову виводять `[K3] wifi disconnect` і `disconnected`; повідомлення про reconnect до збереженої мережі чи отримання IP немає. `status` при цьому хибно показує `WiFi: connected` із порожнім SSID, IP `0.0.0.0` і RSSI `0 dBm` (також зафіксовано в BUG-01).
- **Доказ (фрагмент UART):**
  ```text
  I (1661984) wifi station: button 3 pressed (GPIO39)
  I (1661984) wifi station: [K3] wifi disconnect
  I (1661984) wifi station: disconnected
  ---- Sent utf8 encoded message: "status\n" ----
  I (1673974) wifi station: WiFi: connected
  I (1673974) wifi station:   SSID:
  I (1673974) wifi station:   IP:   0.0.0.0
  I (1673974) wifi station:   RSSI: 0 dBm
  I (1715334) wifi station: [K3] wifi disconnect
  I (1715334) wifi station: disconnected
  ---- Sent utf8 encoded message: "status\n" ----
  I (1726934) wifi station: WiFi: connected
  I (1726934) wifi station:   SSID:
  I (1726934) wifi station:   IP:   0.0.0.0
  I (1726934) wifi station:   RSSI: 0 dBm
  ```
  Повні докази: 1.3.0 — [`logs/manual/wifi/1.3.0/k3-reconnect-1.3.0.txt`](logs/manual/wifi/1.3.0/k3-reconnect-1.3.0.txt); 1.4.0 — [`logs/automated/lamp/1.4.0/20261012-test_k3_reconnects_saved_wifi.txt`](logs/automated/lamp/1.4.0/20261012-test_k3_reconnects_saved_wifi.txt).
- **Відтворюваність:** на 1.3.0 — 2/2 повторних натискань K3 після відключення; на 1.4.0 — перше повторне натискання після відключення. Reconnect не почався.

### BUG-03: Фізичні кольори red/green та purple/cyan переплутані

- **Версія, в якій знайдено:** 1.3.0.
- **Інші версії, у яких відтворюється:** не перевірено (1.4.0, 1.5.0).
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** ESP32-S3 працює на прошивці 1.3.0; лампа доступна для керування.
- **Кроки відтворення:**
  1. Увімкнути лампу командою `lamp on`.
  2. Виконати `lamp color red` і перевірити фактичний колір світлодіода.
  3. Повторити для `lamp color green`, `lamp color purple` та `lamp color cyan`.
  4. Вимкнути та знову увімкнути лампу; повторно перевірити кольори.
- **Очікуваний результат:** фізичний колір відповідає заданому: red — червоний, green — зелений, purple — фіолетовий, cyan — блакитний/ціан; задані RGB значення відповідають FR-L2, а фізичний колір — FR-L4 ([FR-L2](../fw_6/PRD.md#4-smart-lamp), [FR-L4](../fw_6/PRD.md#4-smart-lamp)).
- **Фактичний результат:** фізичні red та green переплутані між собою; purple та cyan також переплутані між собою. Команди та `lamp status` повертають очікувані назви/RGB для заданого кольору (наприклад, після `lamp color red` JSON показує `"color":[255,0,0]`), але ця інформація описує запитане програмне значення, а не колір, який реально випромінює LED. Через це статус суперечить фізичному стану LED, що також порушує FR-L8. Вимкнення та повторне ввімкнення лампи ситуацію не змінює.
- **Доказ:** UART-лог команд та відповідей — [`logs/manual/lamp/1.3.0/lamp-colors-1.3.0.txt`](logs/manual/lamp/1.3.0/lamp-colors-1.3.0.txt); фактичну невідповідність кольорів підтверджено візуальним спостереженням під час тесту.
- **Відтворюваність:** 2/2; обидва рази кольори переплутані, цикл вимкнення/повторного ввімкнення не виправив поведінку.

### BUG-04: Некоректний RGB повертає неправильне повідомлення про помилку

- **Версія, в якій знайдено:** 1.3.0.
- **Інші версії, у яких відтворюється:** не перевірено (1.4.0, 1.5.0).
- **Severity:** Minor.
- **Priority:** P2.
- **Передумови:** ESP32-S3 працює на прошивці 1.3.0; Smart Lamp доступна; перед тестом задано будь-який чинний колір.
- **Кроки відтворення:**
  1. Надіслати команду `lamp color 300 0 0`.
  2. Переглянути відповідь пристрою.
  3. Перевірити, чи змінився колір після відхилення команди.
- **Очікуваний результат:** пристрій відповідає `error: rgb values must be 0-255` і не змінює поточний колір ([FR-L3](../fw_6/PRD.md#4-smart-lamp)).
- **Фактичний результат:** команда `lamp color 300 0 0` один раз із трьох повернула `unknown command, type 'help' for available commands`; у двох наступних повторах тієї самої команди пристрій повернув очікуване `error: rgb values must be 0-255`. Інші перевірені невалідні значення (`0 0 300`, `-1 -1 -1`, `256 0 0`, `300 0 0 ` із пробілом наприкінці, `999 999 999`) також повернули очікуване повідомлення. Попередній колір залишався незмінним.
- **Доказ (фрагмент UART):**
  ```text
  ---- Sent utf8 encoded message: "lamp color 300 0 0\n" ----
  lamp color 300 0 0
  I (3002434) wifi station: unknown command, type 'help' for available commands

---- Sent utf8 encoded message: "lamp color 300 0 0\n" ----
lamp color 300 0 0
E (3192444) wifi station: error: rgb values must be 0-255
  ```
  Повний лог повторної перевірки: [`logs/manual/lamp/1.3.0/lamp-invalid-rgb-retest-1.3.0.txt`](logs/manual/lamp/1.3.0/lamp-invalid-rgb-retest-1.3.0.txt). Первинний лог першого відхилення не знайдений у робочому дереві; відповідний UART-фрагмент збережено вище у звіті.
- **Відтворюваність:** 1/3 для тієї самої команди `lamp color 300 0 0`; інші два повтори пройшли очікувано. Попередній колір не змінився.

### BUG-05: Недопустима яскравість приймається та змінює фізичний колір LED

- **Версія, в якій знайдено:** 1.3.0.
- **Інші версії, у яких відтворюється:** не перевірено (1.4.0, 1.5.0).
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** ESP32-S3 працює на прошивці 1.3.0; лампа увімкнена; встановлено відомий колір (у наданому прогоні — yellow, RGB `[255,180,0]`).
- **Кроки відтворення:**
  1. Виконати `lamp color yellow` і перевірити `lamp status`.
  2. Надіслати значення яскравості поза діапазоном, наприклад `lamp brightness -5` та `lamp brightness 150`.
  3. Спостерігати за фізичним кольором LED і перевірити результат командою `lamp status`.
- **Очікуваний результат:** значення поза діапазоном 0–100 відхиляються з `error: brightness must be 0-100`; попередня яскравість і фізичний вихід лампи не змінюються ([FR-L5](../fw_6/PRD.md#4-smart-lamp)).

При таких значеннях фізичний колір LED змінюється. `lamp status` відображає заданий колір yellow (`[255,180,0]`) і значення яскравості, але не показує фактичну зміну кольору світлодіода.

  ```text
  ---- Sent utf8 encoded message: "lamp brightness 150\n" ----
  I (486496) wifi station: [LAMP] brightness set: 150%
  {"lamp":"on","color":[255,180,0],"brightness":150,"mode":"solid","timer_s":0}
  {"lamp":"on","color":[255,180,0],"brightness":-50,"mode":"solid","timer_s":0}
  ```

- **Відтворюваність:** в одному прогоні відтворено з сімома недопустимими значеннями (`-5`, `-50`, `110`, `120`, `130`, `150`, `200`); кількість окремих повторних прогонів не зафіксована.

### BUG-06: Після переривання OTA повторна спроба блокується до перезавантаження

- **Версії, у яких відтворюється:** 1.3.0 і 1.5.0.
- **Версія, де не відтворився:** 1.4.0 — після обриву Wi-Fi автоматично відновився, повтор `ota update beta` успішно почався без ручного reboot.
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** ESP32-S3 підключена до Wi-Fi; поточна прошивка справна (`state: valid`); OTA-завантаження розпочато й досягло прогресу.
- **Кроки відтворення:**
  1. Запустити OTA (`ota update`, `ota update beta` або same-version `ota install`) і під час прогресу перервати Wi-Fi.
  2. Дочекатися `[OTA] failed: download interrupted (...)` і перевірити, що поточна версія лишилася робочою.
  3. Після відновлення Wi-Fi повторити OTA-команду без перезавантаження.
- **Очікуваний результат:** за OTA-6 завантаження завершується помилкою, пристрій залишається на поточній прошивці, а після відновлення Wi-Fi наступна OTA-спроба одразу працює без reboot.
- **Фактичний результат:** на 1.3.0 автоматичний Wi-Fi reconnect відбувся, але `ota status` і повторний `ota update` відповіли `[OTA] error: update already in progress`; після ручного reboot пристрій лишився на 1.3.0/`ota_0`/`valid`. На 1.5.0 повторні перервані OTA (same-version із force і без нього, а також force-downgrade) залишили ту саму помилку при повторі. У наданому транскрипті від 2026-10-12 пристрій отримав IP перед OTA; після обриву автоматичні reconnect-спроби завершилися `connect to the AP fail`, версія лишилася 1.5.0/`ota_0`/`valid`, а наступний `ota install 1.5.0` без reboot був відхилений як `update already in progress`. Оператор додатково повідомив, що вручну відновити Wi-Fi без reboot також не вдалося; самі команди та результат ручного `connect` у наданому транскрипті не збережені, тому це операторське спостереження, а не окремо перевірюваний фрагмент UART. На 1.4.0 той самий клас помилки не спостерігався: після автоматичного reconnect retry завершився успішним OTA до 1.5.0.
- **Докази (UART):**
  ```text

  [OTA] failed: download interrupted (ESP_FAIL)

  [OTA] error: update already in progress

  # 1.5.0 — автоматичний reconnect не вдався; поточний образ лишився valid
  ```

  Повні докази: [`logs/manual/ota/1.3.0/ota-interruption-retry-1.3.0.txt`](logs/manual/ota/1.3.0/ota-interruption-retry-1.3.0.txt), [`20261012-ota-interruption-retry-1.5.0.txt`](logs/manual/ota/1.5.0/20261012-ota-interruption-retry-1.5.0.txt), [`logs/manual/ota/1.5.0/ota-interruption-same-version-retry-1.5.0.txt`](logs/manual/ota/1.5.0/ota-interruption-same-version-retry-1.5.0.txt), [`logs/manual/ota/1.5.0/ota-interruption-force-downgrade-1.5.0.txt`](logs/manual/ota/1.5.0/ota-interruption-force-downgrade-1.5.0.txt). - **Відтворюваність:** 1.3.0 — 1/1 зафіксований обрив із повторною командою, заблокованою до reboot; 1.5.0 — кілька зафіксованих перерваних OTA-сценаріїв із тим самим результатом; 1.4.0 — 0/1, retry після автоматичного reconnect успішний. Не трактувати різні типи OTA на 1.5.0 як незалежні повтори одного ідентичного сценарію.

### BUG-07: OTA 1.4.0 → 1.5.0 скидає Wi-Fi та налаштування лампи

- **Версія, в якій знайдено:** 1.5.0 після OTA з 1.4.0.
- **Інші версії, у яких відтворюється:** не перевірено.
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** FW 1.4.0 підключена до Wi-Fi; збережений стан лампи — color `[0,0,255]`, brightness `42`, mode `breathe`.
- **Кроки відтворення:**
  1. Перед OTA виконати `version`, `status` та `lamp status`, зафіксувати стан.
  2. Виконати `ota update beta` і дочекатися успішного переходу на 1.5.0 та self-check.
  3. Після reboot перевірити підключення Wi-Fi та `lamp status`.
- **Очікуваний результат:** Wi-Fi credentials і налаштування лампи зберігаються після OTA; не потрібно повторно налаштовувати пристрій (OTA-8, FR-W3, FR-L9).
- **Фактичний результат:** OTA успішне, але після reboot для Wi-Fi повторно введено SSID та пароль; стан лампи замість синього / 42% / breathe став білим / 50% / solid. Пароль у збереженому логу замасковано.
- **Доказ:** [`logs/manual/ota/1.4.0/ota-update-beta-1.4.0-to-1.5.0.txt`](logs/manual/ota/1.4.0/ota-update-beta-1.4.0-to-1.5.0.txt).
- **Відтворюваність:** 1/1.

### BUG-08: Раніше збережена сцена 1 відсутня після OTA на 1.5.0

- **Версія, в якій знайдено:** 1.5.0 після OTA `ota_1` → `ota_0`.
- **Інші версії, у яких відтворюється:** не перевірено.
- **Severity:** Major.
- **Priority:** High.
- **Передумови:** COM4 на FW 1.5.0 (`ota_1`); автотест `test_scenes_by_version[1]` зберіг scene 1 у NVS з color `[17,34,51]`, brightness `37`, mode `solid`. Оператор підтвердив, що перед наступною перевіркою NVS/flash не очищали.
- **Кроки відтворення:**
  1. Зберегти сцену командою `lamp scene save 1` на FW 1.5.0.
  2. Виконати OTA на FW 1.5.0 і дочекатися self-check та `state: valid`.
  3. Виконати `lamp scene load 1`.
- **Очікуваний результат:** сцена 1 та її color, brightness і mode збережені в NVS після OTA; команда повертає `[LAMP] scene 1 loaded` (FR-L10).
- **Фактичний результат:** після `ota install 1.5.0` завантажено `ota_0`, FW 1.5.0; self-check пройшов. `lamp scene load 1` повернула `error: scene 1 is empty`, хоча автотест раніше зберігав її у `ota_1` і NVS не стирали (за підтвердженням оператора). Команда обробила фактичний порожній слот правильно; невідповідність вимозі — збережена сцена відсутня після OTA. Під час boot також відбулася міграція CFG до v2 та виведено warning про 16 MB flash / 2 MB image header; зв'язок цих повідомлень із втратою scene не встановлено.
- **Докази:** до OTA — [`20261012-test_scenes_by_version_1.txt`](logs/automated/lamp/1.5.0/20261012-test_scenes_by_version_1.txt); повний повторний OTA і перевірка після — [`20261012-ota-same-version-scene-load.txt`](logs/manual/lamp/1.5.0/20261012-ota-same-version-scene-load.txt). Відсутність NVS erase підтверджена оператором.
- **Відтворюваність:** 1/1 підтверджений перехід.

## 6. Висновок

- **Статус перевірок:** результати записані для O-01–O-12; серед них 8 PASS, 3 FAIL (O-04, O-05, O-07) і 1 PARTIAL (O-12). BUG-06 оформлено за OTA-6: повторна OTA блокується після обриву на 1.3.0 і 1.5.0; на 1.4.0 retry після автоматичного reconnect успішний. Для нового 1.5.0 транскрипту зафіксовано невдалий автоматичний Wi-Fi reconnect і відмову OTA retry без reboot; ручний `connect` після цього обриву в ньому не наведено. O-12 (`ota broken`, OTA-10) підтверджено двома прогонами з rollback на 1.3.0 і `state: valid`; post-rollback lamp state є лише спостереженням без початкового baseline, тому retention налаштувань лишається непідтвердженим. OTA-10 не є тестом пошкодженого образу OTA-11. O-13 (OTA-11) окремо не запускався. Повний OTA-транскрипт для перевірки BUG-08 додано; він зафіксував CFG migration v2 та flash/header size mismatch. O-14 PASS: `ota <URL>` успішно оновила 1.3.0 → 1.4.0; `ota-test-server` завершила демо та reboot на 1.3.0, 1.4.0 і 1.5.0. Для 1.3.0 та 1.5.0 початкові й фінальні version/partition підтверджують незмінність стану; лог 1.4.0 містить лише результат після reboot, тому не підтверджує стан до запуску. Попередній ввід `ota test server` із пробілами був некоректним і не є результатом перевірки команди з PRD. Custom URL downgrade без force заблоковано, а додавання `force` як суфікса URL спричинило parse error; окремо правильна команда `ota install <version> force` раніше успішно виконала downgrade.
- **Результати OTA HW-16:** 8 PASS, 3 FAIL (O-04, O-05, O-07), 1 PARTIAL (O-12), 0 BLOCKED і 0 NOT RUN серед пунктів O-01–O-12.
- **Чи можна переводити 1.5.0 з beta у stable:** ні, наявних результатів недостатньо для схвалення.
- **Обґрунтування:** O-04 виявив втрату Wi-Fi credentials і налаштувань лампи після OTA, а BUG-08 — відсутність раніше збереженої сцени 1 після OTA на 1.5.0; BUG-06 підтверджує блокування OTA retry після обриву на 1.3.0 і 1.5.0, на відміну від успішного retry на 1.4.0. Для додаткового 1.5.0 логу автоматичне відновлення Wi-Fi не відбулося, а ручний `connect` після обриву не задокументовано; це обмеження зафіксовано, але не скасовує пряме спостереження `update already in progress`. 1.5.0 не слід переводити з beta у stable.
- **Комплект здачі:** у робочому дереві не знайдено архіву `HW-16_<Прізвище>.zip`; за вимогою завдання його ще потрібно сформувати з `REPORT.md` і перевіреною папкою `logs/`. Перед архівацією перевірити повноту OTA-транскриптів і відсутність секретів.
